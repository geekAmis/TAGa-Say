# Безопасность платформы ботов (сервер 1.2.0)

Документ описывает реальное состояние релиза 1.4.0 / сервер 1.2.0. Всё, что
не включено, помечено `[~]` и не выдаётся за сделанное. Связанные документы:
[bot-api.md](bot-api.md), [botfather.md](botfather.md),
[decisions.md](decisions.md) (ADR-004…009), [threat-model.md](threat-model.md).

## 1. Границы доверия

```
Пользователь A ──E2EE──► relay TAGa-Say ◄──TLS──► bot gateway ──HTTPS──► bot server
Пользователь B ──E2EE──►        ▲
                                └── plaintext только для бот-чатов
```

1. Пользователь ↔ пользователь остаётся E2EE; бот не получает ключи,
   `encrypted state`, контакты, телефоны, историю и чужие чаты.
2. Бот-чат **не E2EE**: сообщения боту идут по TLS в открытом виде, хранятся
   в отдельном `BotStore`. Клиент обязан показывать «бот» и «не E2EE».
3. Бот не читает историю до добавления; метода истории в Bot API нет.
4. Сервер проверяет права на каждом запросе; клиент — не источник истины.
5. Бот и пользователь ходят разными API (`/bot/v1` и `/v1/bots`), токены
   не взаимозаменяемы.

## 2. Токены

- Формат: `taga_bot_<numericId>.<base64url-secret>`, секрет 32 байта CSPRNG.
- В `bots.json`:
  - `tokenHash = HMAC-SHA256(pepper, token)` — O(1)-проверка, сравнение
    `MessageDigest.isEqual`;
  - `tokenCiphertext = AES-256-GCM(encKey, token)` — только для явного показа.
- `pepper` и `encKey` — независимые подключи HKDF-SHA256 из
  `TAGASAY_BOT_TOKEN_KEY` (info `taga/bot/token/hmac` и `.../enc`).
- Production (`TAGASAY_ENV=production` или `TAGASAY_PRODUCTION=1`) **не
  стартует** без ключа; debug использует детерминированный локальный ключ.
- Файлы `bots.json`, `bot-updates.jsonl`, `bot-chats.jsonl` — права `600`,
  атомарная замена, JSONL с `fsync`.
- Токен не пишется в логи, URL, уведомления, audit, crash-отчёты. Audit:
  только `botId`, действие (`create`/`revoke`/`delete`), время.
- `/revoke` (BotFather или `POST /v1/bots/{u}/revoke`) помечает все токены
  отозванными и выпускает новый; старый сразу получает 401.
- `lastUsedAt` обновляется в памяти и не переписывает снапшот на каждый запрос.
- Ротация мастер-ключа `[~]`: без неё `/token` не покажет старый секрет, но
  авторизация продолжится по HMAC; процедура — отдельная задача.

## 3. Аутентификация и scopes

- Bot API: `Authorization: Bearer <token>`; токен только в заголовке.
- Проверка: формат → numericId → активный бот → HMAC → не отозван.
  Удалённый бот → 401.
- Scope на метод: `updates:read`, `messages:send/edit/delete`,
  `files:read/write`, `chats:read/manage`, `webapp`, `inline`.
  По умолчанию — минимальный набор без `chats:manage`, `webapp`, `inline`.
- `getMe` возвращает capabilities/scopes; владелец видит свои scopes.
- Пользовательский API использует access token пользователя; владелец
  проверяется на каждом управляющем действии (чужой бот → 403/404).

## 4. `/start`-gate и блокировки

- `bot_user_started` фиксируется при первом `/start`.
- `sendMessage` в `u:<user>` до `/start` → 403; после → ok.
- `/stop` ставит `blocked_at`; отправка → 403. `/start` снимает блокировку.
- `POST/DELETE /v1/bots/{u}/block` — то же из UI; блокировка сильнее scope.
- Бот не может обойти gate: проверка в `BotService.sendMessage`, не в роуте.
- Клиент не доверяет себе: даже если UI покажет поле ввода, сервер вернёт 403.

## 5. Callback-кнопки

- `callback_data` ≤64 байт UTF-8; сервер проверяет, что данные реально есть
  во `reply_markup` сообщения этого бота и этого чата.
- Для BotFather данные подписаны HMAC-SHA256(owner|action|botId), 8 байт;
  чужая/подделанная кнопка → отказ.
- `callback_query_id` живёт 15 минут, одноразовый; ответ бота — через
  `answerCallbackQuery`, текст попадает пользователю событием `callback_answer`.
- Кнопка не является авторизацией: любые действия повторно проверяют владельца.

## 6. Webhook и SSRF `[~]`

В 1.2.0 webhook **не включён**: `setWebhook`/`deleteWebhook`/`getWebhookInfo`
возвращают `400 unsupported`. Проектные ограничения (ADR-007) обязательны при
включении:

- только HTTPS, порт 443/8443, без userinfo/redirect;
- DNS-резолв перед каждой доставкой; запрет loopback/private/link-local/
  multicast/`169.254.169.254`/IPv6 ULA; повторная проверка при каждой попытке
  (DNS rebinding); подключение по проверенному IP с корректным `Host`;
- таймаут 5 с, 3 ретрая с экспоненциальной задержкой, `last_error`;
- подпись `X-TAGa-Say-Signature: sha256=HMAC(secret, timestamp.body)` и
  `X-TAGa-Say-Bot-Api-Secret-Token`;
- webhook и `getUpdates` взаимоисключающие (409); `max_connections` ≤10.

Загрузка файлов по произвольному URL запрещена (SSRF): только multipart или
ранее выданный `file_id` — когда файлы появятся (`[~]`).

## 7. Web App и initData `[~]`

Не включено в 1.2.0: `/setdomain`, `/newapp`, `web_app`-сессии и
`answerWebAppQuery` отвечают 400. Проектные правила (ADR-008):

- `initData` подписывается HMAC-SHA256 ключом бота, содержит `auth_date`,
  `query_id`, `user`, `chat_instance`, `start_param`;
- TTL 5 минут, `query_id` одноразовый, домен — только из allowlist;
- `web_app` кнопки — только личный чат и только зарегистрированный домен;
- WebView: HTTPS-only, allowlist, `setAllowFileAccess(false)`,
  `setAllowContentAccess(false)`, без mixed content/третьих cookies;
- JS-мост не даёт доступ к vault, ключам, файлам и токенам приложения;
  закрытие уничтожает WebView.

Сейчас `web_app`-кнопка проходит валидацию только если у бота уже задан
`domain` (вручную/будущим `/setdomain`); иначе 400 — честно, без имитации.

## 8. Файлы `[~]`

P1: `BotMediaStore` с TTL 30 дней, лимит 50 МБ, MIME по magic bytes,
случайные имена, запрет `..`/абсолютных путей/symlink, HTML/SVG не рендерятся
inline, `file_id` привязан к боту (чужой → 404). В 1.2.0 `attachment_id` и
`sendPhoto`/`getFile` возвращают 400.

## 9. Rate limits и антиспам

| Лимит | Значение |
|---|---|
| sendMessage на бота | 30/с |
| sendMessage в один чат | 1/с (считается только успешная отправка) |
| getUpdates | 20/мин на бота |
| BotFather | 20 команд/мин на владельца |
| user → bot | 60/мин на пользователя |
| управление ботом | 60/мин на владельца |
| поиск/карточки | 120/мин на IP |
| inbox long-poll | 240/мин на IP |

429 c `retry_after`. Лимиты в памяти процесса; при нескольких инстансах
потребуется Redis `[~]`.

## 10. Логи и приватность

- CallLogging: только `method -> status`, без пути, query, тела и заголовков.
- Запрещено логировать: текст сообщений, токены, `@username`, имена файлов,
  `file_id`, IP (audit — без IP).
- Ошибки Bot API возвращают описание без внутренних деталей; стектрейсы не
  уходят клиенту.
- `getMe` не отдаёт владельца и токен.
- Карточка в `/v1/bots` не содержит `owner`.

## 11. Ретеншн и удаление

| Данные | Срок/лимит |
|---|---|
| updates | 10 000 / 7 дней на бота, затем ring buffer |
| бот-сообщения | 30 дней, 5 000 на бота |
| callback-ответы | 1 000 |
| удалённый бот | `deleted`, username свободен сразу, данные до 30 дней |
| audit | 1 000 записей |

Удаление бота не стирает сообщения мгновенно (нужны tombstone для клиента);
бот не может «воскресить» удалённые данные. `panic-wipe` на клиенте должен
чистить бот-чаты, кеш бот-файлов, WebView storage и настройки ботов — это
клиентская часть (вне этого batch) `[~]`.

## 12. Остаточные риски

1. **Plaintext бот-чатов** — осознанный компромисс; дамп `BotStore` раскрывает
   переписку с ботами. Локальная копия на устройстве — основная.
2. **JSON/JSONL без транзакций** — один инстанс; при росте нужна PostgreSQL.
   Потеря последней строки JSONL при жёстком сбое возможна, но updates
   переживают штатный рестарт.
3. **Мастер-ключ** — компрометация env + `bots.json` раскрывает все токены;
   ключ хранится только в окружении/файле `600`.
4. **Rate limits в памяти** — не распределённые.
5. **`/token` в чате** — токен лежит в plaintext-сообщении до 30 дней; это
   требование UX (как в Telegram), предупреждение показывается.
6. **Нет webhook/файлов/Web App** — функциональные `[~]`, не «дыры»: методы
   возвращают 400, а не делают вид, что работают.
7. **BotFather нельзя удалить**; при занятом username встроенный бот не
   создаётся и пишется предупреждение — данные не переименовываются молча.

## 13. Чем подтверждено

`server: test` (Ktor test-host, 29 тестов, все зелёные), в том числе:

- валидный/битый/отозванный токен, удалённый бот;
- scope denial, rate limit;
- 403 до `/start`, ok после, 403 после `/stop`, разблокировка `/start`;
- чужой бот: `/mine`, delete/revoke/token → 403;
- занятый username, reserved, лимит 20;
- getUpdates offset/ack/отсутствие дублей;
- BotFather happy path, `/token`, `/revoke` (старый 401), `/deletebot`,
  `/cancel`, таймаут FSM, занятый username;
- рестарт `BotStore`, конкурентная запись, битый `.tmp`/JSONL;
- edit/delete только своих сообщений, unsupported → 400.

Ручная проверка на устройстве/боевом сервере — задача принимающего релиз
(этот batch не деплоится).
