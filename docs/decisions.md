# Решения (ADR)

Короткие записи о спорных архитектурных решениях. Формат: контекст → решение →
последствия.

## ADR-001. Ключ состояния пользователя

**Контекст.** Состояние (профиль, папки, стикеры, звонки, контакты, каналы,
истории) синхронизируется через relay. Первая версия выводила ключ из
Argon2id-verifier пароля. Verifier отправляется на сервер, поэтому сервер мог
расшифровать состояние — грубое нарушение модели угроз.

**Решение.** Генерировать на устройстве случайный 256-битный AccountMasterKey,
хранить его только в обёрнутом виде на ключе Android Keystore, а ключ состояния
выводить как `HKDF(master, salt=username, info="taga/state/v2")`. Сервер получает
только AES-256-GCM ciphertext. Старый формат v1 расшифровывается один раз для
миграции и перезаписывается в v2.

**Последствия.**
- Сервер и дамп БД не могут расшифровать состояние без master-ключа.
- После полного удаления приложения master-ключ теряется: восстановление
  состояния возможно только после реализации привязки устройств (этап 5).
- Мультиустройство потребует обернуть master-ключ на ключ каждого устройства
  (X25519 + HKDF + AES-GCM). До этого состояние синхронизируется только в
  пределах одного устройства/переустановки с сохранённым Keystore.

## ADR-002. Группы и каналы: pairwise fan-out

**Контекст.** Для E2EE-групп нужен Sender Keys или попарное шифрование.
libsignal Sender Keys в текущей сборке не подключён.

**Решение (план).** На первом этапе — попарный fan-out: отправитель шифрует
сообщение каждому участнику через существующую 1:1-сессию. Сервер хранит только
список участников и пересылает конверты. При исключении участника новые
сообщения ему просто не отправляются.

**Последствия.**
- Работает без нового криптопротокола и без Sender Keys.
- Стоимость отправки O(участников), сервер видит граф группы.
- Нет истории для нового участника без отдельного механизма.
- Sender Keys — следующий шаг для больших групп.

## ADR-003. Сервер: JSON-снапшот вместо PostgreSQL

**Контекст.** Нужен быстрый путь к работающему продукту и простой бэкап.

**Решение.** Пока оставить `InMemoryStore` с атомарным JSON-снапшотом и
`Mutex`; PostgreSQL/Redis/Testcontainers — отдельный этап.

**Последствия.**
- Нет транзакций, индексов и горизонтального масштабирования.
- Снапшот переживает рестарт, но не подходит для большой нагрузки.
- Все новые сущности (state, rooms) добавлены в снапшот с версионными полями.

## ADR-004. Бот-чаты — plaintext, не E2EE

**Контекст.** Бот — внешняя доверенная конечная точка, у которой нет ключей
Signal-сессии. Шифровать сообщения боту бессмысленно: он всё равно должен их
прочитать. При этом пользователь ↔ пользователь обязан остаться E2EE.

**Решение.** Личная переписка с ботом и сообщения, адресованные боту в
группе/канале, идут на сервер по TLS в открытом виде и хранятся в отдельном
`BotStore` (не в пользовательском снапшоте и не в E2EE-конвертах). Клиент
обязан показывать «бот» и «не E2EE» в шапке бот-чата и предупреждение при
первом `/start`. Сервер не даёт боту доступ к `/v1/state`, ключам, контактам,
телефонам, истории и чужим чатам. Ответы бота в группе — plaintext для всей
комнаты; входящее адресованное сообщение уходит людям обычным E2EE, а боту —
отдельной plaintext-копией.

**Последствия.**
- Дамп `BotStore` раскрывает переписку с ботами; это осознанный компромисс.
- Ретеншн бот-переписки — 30 дней (ADR-010), локальная копия на устройстве
  остаётся основной.
- В логи не попадают текст, `@username`, имена файлов и токены (§6.2 ТЗ).

## ADR-005. Хранение и выдача бот-токенов

**Контекст.** Токен нужен для O(1)-проверки на каждом запросе Bot API и для
повторного показа владельцу по `/token`, как в Telegram. Хранить только хеш
нельзя — токен не восстановить; хранить только шифртекст — проверка станет
дорогой и потребует расшифровки на каждый запрос.

**Решение.** Токен формата `taga_bot_<numericId>.<base64url-secret>` (секрет
32 байта). В `bots.json` лежат одновременно:
- `tokenHash = HMAC-SHA256(pepper, token)` — для O(1)-проверки, сравнение
  constant-time;
- `tokenCiphertext = AES-256-GCM(encKey, token)` — только для явного показа
  владельцу.

`pepper` и `encKey` — разные подключи, выведенные HKDF-SHA256 из мастер-ключа
`TAGASAY_BOT_TOKEN_KEY` (info `taga/bot/token/hmac` и `taga/bot/token/enc`).
Production без ключа **не стартует** (fail-fast); debug/локально используется
детерминированный ключ, чтобы тесты и dev-сервер переживали рестарт. Ключ не
коммитится, файлы `bots.json`/`bot-*.jsonl` — права `600`. Токены никогда не
логируются, не попадают в URL, уведомления и audit (там только bot id, время,
действие). `/revoke` помечает все токены отозванными и выпускает новый; старый
токен сразу получает 401. Ротация мастер-ключа — отдельная процедура: без неё
`/token` не покажет старый секрет, но авторизация продолжит работать по HMAC.

**Последствия.**
- Компрометация `bots.json` без мастер-ключа не даёт токенов.
- Компрометация мастер-ключа + `bots.json` раскрывает все токены — ключ
  хранится только в env/файле `600` и входит в бэкап.
- HMAC, а не Argon2id: токен высокоэнтропийный, перебор нерелевантен, а
  Argon2id на каждый запрос недопустим по latency.

## ADR-006. BotStore: JSON/JSONL вместо PostgreSQL (сейчас)

**Контекст.** В 1.2.0 нет PostgreSQL/Redis. Нужны независимое от E2EE
хранилище, переживание рестарта и отсутствие перезаписи пользовательского
снапшота на каждое сообщение бота.

**Решение.** Отдельный `BotStore` в каталоге `TAGASAY_BOT_DATA` (или
`<parent of TAGASAY_DATA>/bots`):
- `bots.json` — боты, токены, user states, FSM BotFather, offset'ы, audit;
- `bot-updates.jsonl` — append-only очередь updates (ring buffer 10 000 / 7 дней
  на бота, compaction при разрастании);
- `bot-chats.jsonl` — append-only события сообщений/ответов callback
  (upsert/delete, ретеншн 30 дней, cap 5 000 сообщений на бота).

Запись — через временный файл и `Files.move(ATOMIC_MOVE, REPLACE_EXISTING)` с
fallback; JSONL — `FileOutputStream(...).fd.sync()`. Частично записанная строка
JSONL при старте пропускается. Права `600`. Пользовательский `InMemoryStore`
не трогается.

**Последствия.**
- Нет транзакций, индексов и горизонтального масштабирования; один инстанс.
- При росте нагрузки — миграция на PostgreSQL: те же таблицы (`bots`,
  `bot_tokens`, `bot_updates`, `bot_messages`, `bot_user_states`), offset и
  update_id как последовательности, JSONL-файлы импортируются одноразово.
- Для текущего масштаба (несколько тысяч ботов) этого достаточно; «промышленный
  кластер» не заявляется.

## ADR-007. Webhook и SSRF (проектное решение, в 1.2.0 не включено)

**Контекст.** Webhook требует, чтобы сервер сам ходил по URL, который задал
владелец бота, — это классический SSRF-вектор.

**Решение (на следующий batch).** Только HTTPS, порт 443/8443, без userinfo и
redirect. Перед каждой доставкой резолвить DNS и отклонять loopback, private,
link-local, multicast, `169.254.169.254`, IPv6 ULA/link-local; повторно
проверять при каждой попытке (DNS rebinding), подключаться по уже проверенному
IP с `Host`-заголовком. Таймаут 5 с, 3 ретрая с экспоненциальной задержкой,
`last_error`/`failure_count`; подпись
`X-TAGa-Say-Signature: sha256=HMAC(secret, timestamp.body)` и
`X-TAGa-Say-Bot-Api-Secret-Token`. `getUpdates` и webhook взаимоисключающие
(409). Загрузка файлов по произвольному URL запрещена — только multipart или
ранее выданный `file_id`.

**Последствия.** В 1.2.0 методы `setWebhook`/`deleteWebhook`/`getWebhookInfo`
возвращают честный `400 unsupported` (в доках `[~]`), а не имитацию. Модели
`BotWebhook` уже заложены в `BotStore`, чтобы включить доставку без миграции
формата.

## ADR-008. Web App initData и домены (проектное решение, P1)

**Контекст.** Web App открывается в WebView и получает данные пользователя;
подделка `initData` или чужой домен недопустимы.

**Решение (P1).** `initData` — строка параметров (`auth_date`, `query_id`,
`user`, `chat_instance`, `start_param`), подписанная
`HMAC-SHA256(bot_token, "WebAppData" || data_check_string)`; TTL 5 минут,
`query_id` одноразовый (хранится использованным до истечения TTL). `web_app`
кнопки разрешены только в личном чате и только для домена из allowlist
BotFather (`/setdomain`, `/newapp`); URL — HTTPS, без userinfo/redirect.
JS-мост не даёт доступ к vault, ключам, файлам и токенам приложения; WebView —
HTTPS-only, `setAllowFileAccess(false)`, `setAllowContentAccess(false)`, без
mixed content и сторонних cookies; закрытие уничтожает WebView.

**Последствия.** До реализации `web_app`-кнопки отклоняются с 400, а
`/newapp`, `/setdomain`, `/webapp/session` помечены `[~]`.

## ADR-009. Лимиты, ретеншн и удаление

**Контекст.** Нужно не дать ботам разрастить хранилище и спамить, при этом
честно описать, сколько данные живут.

**Решение.**
- Лимит 20 активных ботов на владельца; удалённый username освобождается
  сразу, старые токены остаются отозванными (401), данные бота чистятся через
  30 дней (в 1.2.0 — статус `deleted`, сообщения доступны только на чтение
  владельцу через BotFather-карточку не показываются).
- Updates: 10 000 на бота, TTL 7 дней, `drop_pending_updates` очищает.
- Личные бот-чаты: 30 дней, cap 5 000 сообщений на бота.
- Файлы (P1): 50 МБ на файл, 30 дней, квоты на бота/пользователя.
- Rate limits: 30 сообщений/с на бота, 1 сообщение/с в один чат,
  20 `getUpdates`/мин, 20 команд BotFather/мин на владельца; 429 с
  `retry_after`.
- Логи: только bot id, метод, код, latency; без текста, `@username`, имён
  файлов и секретов.

**Последствия.** Ретеншн реализован лениво (при старте и операциях), отдельного
cron в 1.2.0 нет; при больших объёмах нужен фоновой cleanup.
