# Модель угроз

## 1. Активы

- Содержимое сообщений и вложений.
- Ключи шифрования и парольная фраза.
- Список контактов и социальный граф (телефон не используется).
- Метаданные: кто, когда, кому, сколько, с какого IP.
- История звонков и медиа.

## 2. Кто угрожает

| Противник | Возможности | Что хотим защитить |
|---|---|---|
| Провайдер / ISP | пассивный и активный MITM, анализ трафика | содержимое, метаданные |
| Оператор сервера | доступ к БД, логам, диску, памяти | содержимое, социальный граф |
| Внешний взломщик сервера | RCE, дамп БД | содержимое, ключи |
| Злоумышленник в сети | перехват, подмена TLS | содержимое, аутентичность |
| Украденное устройство | доступ к ФС, offline-анализ | ключи, история |
| Нелегальный доступ к устройству | принуждение к разблокировке | локальные данные |
| Вредоносный собеседник | вредоносные файлы, фишинг | устройство, данные |
| Массовый сбор | корреляция трафика | метаданные |

## 3. Гарантии

1. **Конфиденциальность содержимого.** Сервер и провайдер не могут прочитать
   сообщения и вложения без ключей устройства.
2. **Целостность и аутентичность.** Подмена конверта обнаруживается (AEAD +
   подпись отправителя).
3. **Прямая секретность.** Компрометация долговременных ключей не раскрывает
   прошлые сессии (Double Ratchet).
4. **Пост-компрометация.** После восстановления сессии новые сообщения защищены.
5. **Минимизация метаданных.** Сервер не хранит открытый ID отправителя в конверте;
   получатель адресуется blinded-токеном.
6. **Локальная защита.** БД и вложения зашифрованы; ключи в Keystore/StrongBox.

## 4. Чего мы НЕ гарантируем

- Защиту от противника с физическим доступом к разблокированному устройству.
- Полную анонимность в сети: IP-адрес виден серверу/TURN. Сокрытие IP — отдельная
  фаза (mixnet/onion), см. roadmap.
- Защиту от screenshot на уровне ОС (используем `FLAG_SECURE` там, где возможно).
- Защиту от компрометации самого клиента (вредоносная ОС, рутованный телефон).
- Достоверность личности собеседника без ручной верификации отпечатков/QR.
- Защиту метаданных от глобального пассивного наблюдателя (timing/size correlation);
  применяем паддинг, батчинг и jitter, но это не mixnet.

## 5. Ключевые решения и компромиссы

### 5.1. Ключи из данных устройства + соль сервера
По требованию проекта мастер-ключ может выводиться как
`HKDF(device_secret, server_salt, user_passphrase)`.
**Важно:** «данные устройства» (модель, Android ID, IMEI и т.п.) не являются секретом —
они предсказуемы и доступны приложениям. Поэтому:
- основная энтропия — случайный 256-битный секрет, сгенерированный в Keystore;
- `server_salt` — публичная константа, добавленная как domain separation, а не секрет;
- `user_passphrase` усиливается Argon2id;
- итоговый ключ не покидает TEE/StrongBox, где это возможно.

Это даёт привязку к серверу и устройству, но без иллюзии, что серийный номер телефона
что-то защищает.

### 5.2. Антивирус при E2EE
Сервер не видит файлы, поэтому проверка выполняется:
- на устройстве отправителя до отправки;
- на устройстве получателя после расшифровки;
- по хешу — через репутационные списки (без передачи файла).
Опциональная серверная проверка возможна только с явного согласия и в песочнице.

### 5.3. Идентификация и contact discovery
Телефон не используется. Аккаунт = `@username` + Argon2id-verifier пароля + уникальный
device hash. Поиск — по `@username` и deep link. 2FA (TOTP) защищает повторную
регистрацию/вход на новом устройстве.

### 5.4. Push-уведомления
FCM видит токен устройства и факт push. Содержимое не передаётся: клиент
расшифровывает сообщение локально после пробуждения. Для повышенной приватности —
опция «без push» (только foreground/periodic sync).

## 6. Атаки и меры

| Атака | Мера |
|---|---|
| MITM на TLS | TLS 1.3 + pinning + HSTS |
| Подмена prekey | подпись signed prekey, TOFU + QR-верификация |
| Replay | монотонные счётчики ratchet, дедупликация ID |
| Downgrade | версия протокола в AAD, отказ от старых версий |
| Анализ размера | паддинг до классов, батчинг |
| Анализ времени | jitter, задержка отправки, cover traffic (частично) |
| Zip-bomb | лимиты распаковки, проверка заголовков |
| Вредоносный файл | YARA, сигнатуры, sandbox по согласию |
| Кража устройства | Keystore, биометрия, panic-wipe, запрет backup |
| Компрометация сервера | E2EE, отсутствие ключей на сервере |
| Принуждение к выдаче | отсутствие ключей у оператора, plausible deniability (в перспективе) |

## 7. Остаточные риски

- Корреляция трафика глобальным наблюдателем.
- Компрометация цепочки поставок зависимостей.
- Уязвимости в WebRTC/libsignal.
- Социальная инженерия.
- Ошибки в собственном коде (снижаем тестами и аудитом).
